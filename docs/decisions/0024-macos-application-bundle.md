# The macOS build is an application bundle, "Jedi Academy.app", for macOS 11 and later, signed ad hoc

## Context and Problem Statement

The macOS presets build a bare executable, `jasp`, with the game module
`jagamearm64.dylib` beside it. A Mac user starts programs from the Finder, which wants
an application bundle: a directory `<name>.app` with the executable in
`Contents/MacOS` and a description of it in `Contents/Info.plist`. The M3 roadmap asks
for one ([design document](../design.md), section 8). Building it raises questions no
record answers:

* what the bundle is called, and its identifier, which macOS uses to tell apps apart;
* where the game module lies, and how the engine finds it. Inside a bundle,
  `SDL_GetBasePath`, which the engine uses for "the directory of the executable", names
  `Contents/Resources`, and code there breaks the bundle's signature;
* which version of macOS the build needs. None is set, so the binaries require the
  version of the SDK they were built with, macOS 15 on CI's runner;
* how the bundle is signed. On arm64, macOS runs no code without a signature.

Where the engine looks for the game data when it is started from the Finder, without a
command line, is decided in [ADR-0025](0025-game-data-asked-for-once.md).

## Decision Drivers

* The window is titled "Jedi Academy", and nothing may suggest an official product
  ([ADR-0020](0020-window-title-and-icon.md)).
* The executable and the module keep their names ([ADR-0010](0010-project-and-binary-names.md)).
* arm64 is the only macOS target ([ADR-0003](0003-target-platforms.md)); every Mac with
  it runs macOS 11 or later.
* One build system, and the bundle built by the same presets
  ([ADR-0004](0004-build-system-and-toolchain.md)).
* No secrets in CI ([ADR-0023](0023-continuous-integration-with-build-dependencies.md)),
  and no paid account the project depends on.

## Considered Options

For signing:

* Ad hoc, by the build
* A Developer ID, and notarisation by Apple

For the place of the game module:

* `Contents/MacOS`, beside the executable
* `Contents/Frameworks`
* `Contents/Resources`, where `SDL_GetBasePath` points

## Decision Outcome

Chosen options: "ad hoc, by the build", because it needs neither an account nor a
secret, and "`Contents/MacOS`", because it is where Apple's layout puts code that is
not a framework, and keeps the module beside the executable as on the other platforms.

* **Name:** the bundle is `Jedi Academy.app`, and shows as "Jedi Academy". The
  executable inside is `jasp`, the module `jagamearm64.dylib`.
* **Identifier:** `io.github.lukad.jasp`, after the public repository.
* **Layout:**
  `Contents/Info.plist`, `Contents/MacOS/jasp`, `Contents/MacOS/jagamearm64.dylib`.
  No icon until the icon is decided ([ADR-0020](0020-window-title-and-icon.md)); macOS
  shows its default.
* **Info.plist:** generated by CMake from a template in `cmake/`, with the name, the
  identifier, the executable, the project's version and `LSMinimumSystemVersion` 11.0.
* **The module** is looked for in the directory of the executable file. On macOS
  inside a bundle, that is `Contents/MacOS`, which `src/sys` derives from the bundle's
  path; elsewhere it is what `SDL_GetBasePath` names, as now.
* **macOS version:** the macOS presets set `CMAKE_OSX_DEPLOYMENT_TARGET` to 11.0, for the
  engine, the module and the libraries the project builds. If a part of the C++20
  library that the code uses needs a later macOS, the build says so, and the version
  is decided again.
* **Signing:** after the bundle is assembled, the build signs it ad hoc
  (`codesign --sign -`). Such a bundle runs on the Mac that built it. Downloaded, it
  carries the quarantine attribute and macOS refuses to open it until the attribute is
  removed (`xattr -dr com.apple.quarantine "Jedi Academy.app"`) or it is opened once
  through the Finder's context menu.
* **CI** builds the bundle in both macOS jobs, as part of the presets. It does not
  publish it.

### Consequences

* Good, because a Mac user starts the game from the Finder.
* Good, because the build runs on every Apple silicon Mac, not only on the newest
  macOS.
* Good, because nothing in the bundle needs an Apple account, and CI stays without
  secrets.
* Bad, because a bundle that was downloaded has to be cleared of its quarantine before
  it opens, and macOS warns about an unidentified developer.
* Bad, because the identifier names the repository's owner; if the project moves, the
  identifier either stays as it is or changes and loses the settings macOS keeps under
  it.
* Neutral, because the per-user directory stays what SDL gives for `jasp`,
  `~/Library/Application Support/jasp/`; it does not depend on the identifier.

### Confirmation

* Both macOS jobs of CI build `Jedi Academy.app` with the layout above, and `codesign
  --verify` accepts it.
* `otool -l` shows a minimum version of 11.0 for the executable and the module.
* On a real Mac, the bundle opens from the Finder and loads its module. That needs a
  person with a Mac, and is part of the exit criteria of M3.

## Pros and Cons of the Options

### Ad hoc signing

* Good, because free, and the linker signs each binary ad hoc already; the bundle only
  needs the same over the whole.
* Bad, because of the quarantine of downloaded copies.

### Developer ID and notarisation

* Good, because a downloaded bundle opens without a warning.
* Bad, because it needs a paid Apple developer account, and its certificate as a
  secret in CI.
* Bad, because the project would ship an identified, notarised build of a game whose
  name is someone else's trademark, which suggests more than an unofficial build should.

### The module in `Contents/MacOS`

* Good, because the executable and the module lie together, as on the other platforms.
* Bad, because the engine needs a few lines that know a bundle's layout.

### The module in `Contents/Frameworks`

* Good, because it is Apple's place for libraries an app links to.
* Bad, because the module is not linked to but loaded by name, and the place would
  differ from the other platforms for no gain.

### The module in `Contents/Resources`

* Good, because `SDL_GetBasePath` already points there; no code changes.
* Bad, because code in `Resources` is not signed as code, and the bundle's signature
  fails.

## More Information

* Apple's bundle layout: "Placing content in a bundle", Apple Developer documentation.
* SDL3's `SDL_GetBasePath` documents that it names `Contents/Resources` in a bundle.
* To be revisited with the icon, and if the project is to be distributed to players.
